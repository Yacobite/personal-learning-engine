# Approved architecture refinements

These user-approved decisions supplement `DESIGN_SPEC.md`, whose original contents are preserved.

## M3 implementation decisions

The user approved the pre-coding graph architecture and the bounded official-documentation adapter. The following details implement that scope:

- A stable course-owned `concept-<UUID v4>` is distinct from each curriculum version's node presentation. Proposal-local keys identify edge endpoints; explicit existing concept IDs request reuse. Titles never allocate or merge identities. Builder manifests include identities from historical versions, including concepts omitted from the latest version.
- Curriculum content is immutable after draft creation. First activation time is lifecycle metadata; the active state derives from one course/version pointer. Activation is an explicit application operation outside the model tool set. Rejected proposals and failed transactions preserve existing curricula.
- Only `prerequisite_of` is a dependency edge in M3, directed prerequisite to dependent. All other supported relations are directed without dependency semantics. Reciprocal non-prerequisite relationships are allowed; duplicate typed edges and all self-relations are rejected as unhelpful in this slice. Node/edge enums are centralized in the domain.
- Proposals reject unknown fields and enforce runtime bounds: 1–500 nodes, up to 2,000 edges, up to 20 source and 20 research references per node, and bounded text/uncertainty. No mastery, learner status, activation or course-mutation fields are accepted. Every node requires provenance; source-grounded nodes use learner evidence, generated nodes use retrieved research, and hybrid nodes can mix them.
- Source references retain course ownership, exact source version and exact segment identity. Anchors are resolved from M2. Relational foreign keys also enforce node/concept ownership and exact segment/source/version alignment. Source reads use a frozen historical build manifest rather than following updated pointers mid-build.
- Research is stored independently of M2 learner sources in briefs and immutable retrieved reference records. The fixed Python adapter supplies actual metadata and explicit failures. Seed topics guide retrieval; synthesized claims live in curriculum nodes with reference links and uncertainty. Hashes identify original HTML response bytes; stored normalized text is supplementary extraction of those bytes.
- Six fixed Python tutorial seed pages are approved. The model can inspect this persisted evidence and submit a proposal; it cannot supply network targets or edit the policy. Public IPv4-only DNS resolution, pinned lookup, peer verification and TLS hostname checks prevent autonomous retrieval from inheriting M2's deferred arbitrary-URL assumptions. Limits are six seeds, two redirects per document, 15 seconds per document, 2 MiB HTML and 16 KiB headers. No crawl, proxy configuration, cookies, authentication, browser or new dependency is introduced.
- Pi 1.0.1 uses `createAgentSession`, explicit tool allowlists, custom JSON-schema tool parameters and a clean resource loader. Its `tool_search` is tool discovery, not web search. The model builder's separate in-memory session exposes two tools only and does not load ambient extensions/MCP/context/skills. This restricts capabilities without claiming an operating-system sandbox. Application services remain independently testable with fake ports.
- Migration 4 is additive and separate from unchanged migrations 1–3. Graph creation and activation use explicit short SQLite transactions. No agent code writes SQL. Markdown reports and compact maps remain supplementary artifacts.
- M3 acceptance used genuinely extracted private Logic text and genuinely retrieved Python documentation. Reviewed proposals were submitted through the model-facing tool. Real Pi SDK command/tool integration was separately tested with a deterministic fake model turn; live Pi provider authentication/completion was not validated on this machine.
- No diagnostic, attempt/evaluation, mastery/readiness, gap, review scheduling, teaching, quiz, web UI, OpenClaw or later specialist-agent behavior enters M3.

- Pi adapters call application services; services depend on domain/policy/port interfaces. Concrete adapters implement ports. Domain modules do not depend on Pi, SQL drivers, providers, terminal UI, or OpenClaw.
- `_learning/learning.db` is canonical application state. Models propose results; validated application/domain operations control durable mutations.
- Active course selection is session-specific and references a persistent course ID. It is not global workspace state.
- Only prerequisite/dependency edges must be acyclic. Other knowledge relationships may form cycles.
- Progression readiness and durable mastery are distinct. Names and thresholds belong to the learner-model milestone.
- Committed learning evidence survives chat branching and navigation.
- Source and curriculum history is version-oriented. Historical evidence must resolve its original source version.
- M0/M1 source contracts stay minimal. Versions, segments, artifacts, anchors, rendering, and retrieval are designed in M2 against real fixtures.
- A minimal researcher execution interface may enter M3 when needed; the full specialist framework stays deferred.
- Basic attempt/evaluation/evidence contracts precede probing; full mastery/gap behavior stays deferred.
- Evidence must be auditable and evaluations correctable without deleting historical attempts.
- YouTube/transcript ingestion stays in V1. Retrieval limitations must be explicit.

## M0 engineering choices

- Pin `@earendil-works/pi-coding-agent` 1.0.1, verified against npm and installed declarations.
- Use Node 24's built-in `node:sqlite`, not an ORM or third-party native addon. The tested Node 24.19.0 runtime provides SQLite 3.53.3 and FTS5.
- Use synchronous SQLite for short foundation operations. Keep driver types in persistence; review long-running work when ingestion is implemented.
- Use `node:test`, native TypeScript stripping, TypeScript 6.0.3, and Node types 24.19.1. TypeScript 7.0.2 was inspected but lacks the stable compiler API used for AST-based boundary checks; 6.0.3 supplies it without an additional parser dependency. No build runner, lint framework, or formatting dependency is needed for M0.
- The migration ledger is the only M0 schema. Each migration is checksummed; unknown/modified history is rejected. Pending changes and ledger entries commit together.
- The composition root opens/closes the database with Pi session events. `/learning-status` only delegates and renders diagnostics.
- Pi is a private project's development host dependency, not an application-domain dependency. This is not yet a distributable Pi package.

## M1 engineering choices

- The minimal Course has ID, title, mode, objective, created timestamp, and updated timestamp. Creation sets both timestamps to the same UTC ISO value; no update/delete operations are introduced.
- IDs use `course-<lowercase UUID v4>`, generated by Node `randomUUID` in the composition root and injected into the service. IDs do not derive from titles. Duplicate titles are allowed; primary-key collisions retry up to three allocations without overwriting existing records.
- Migration 2 adds only `courses`. Migration 1's SQL, name, version, and checksum are unchanged. A fixed M0 ledger fixture verifies upgrade behavior.
- The existing database connection supplies a course repository; `CourseService` owns input validation and operations behind the repository port. One parameterized insert atomically creates each course; storage errors preserve their cause internally and expose a generic message.
- `/course new <mode> "title" "objective"` uses double-quoted JSON-style strings. Other operations are `/course list`, `/course use <id>`, and `/course current`. No model tools or interactive form framework are introduced.
- One `CourseSession` object belongs to each extension runtime's live session. It only references an ID, resolves through `CourseService`, and clears on shutdown/start (including reload or replacement). Creation does not select a course. Selection is not persisted in SQLite or Pi entries.
- No new dependencies, source/ingestion schema, or later-milestone features are added.

## M2 engineering choices

- Source objects belong to one course. `SourceService` coordinates ingestion and retrieval through input-reader, parser and repository ports; parsers return normalized documents without Pi or SQLite dependencies. The Pi adapter only delegates and renders untrusted data.
- IDs use injected `source-<UUID v4>`. Logical identity is course plus normalized project-relative source path (case-insensitive on Windows, `/` separators), final HTTP URL, or canonical YouTube video URL. Local provenance and caption locations are project-relative too; resolved absolute paths are transient safety details. Moving the entire project preserves local identity; moving a source within it/changing a final URL creates another logical source. SHA-256 of original input bytes identifies versions; unavailable captions use a deterministic marker.
- Versions are immutable and unique by source/hash. Changed bytes append; unchanged bytes reuse; reverting selects an existing historical version. Historical extracted text, title, warnings, parser, hash, location, timestamps and anchors are retained. Original binary/HTML snapshots and parser-upgrade/reprocessing policy remain deferred; identical bytes do not replace an existing failed extraction.
- Migration 3 adds sources, source versions, source segments, and FTS5. It enforces lowercase UUID-v4 source IDs (including exact separator positions) and non-empty identities defensively in SQLite. Existing course rows and migrations 1/2 are unchanged. Foreign keys and one transaction protect source/version/current-pointer/index consistency. FTS is a supplementary index of canonical SQLite segments.
- Anchors discriminate physical PDF pages, PPTX slides/notes, Markdown/HTML sections and offsets, text offsets, and caption time ranges. PDF pages are 1-based physical file pages, including slide builds; printed numbers can differ. Empty pages stay addressable. Visual references identify deferred extraction, not understood visuals.
- PDF uses native page text; every PDF carries the visual limitation, and pages below 40 extracted characters carry page-specific limitations. No OCR/vision pipeline is implemented. PPTX follows presentation relationships then XML shape order, with labeled notes. Markdown supports ATX/setext headings and fenced code; text is bounded at 4,000 UTF-16 units. HTML parsing uses static main/article/body heuristics without executing scripts.
- YouTube uses explicitly supplied project-local WebVTT captions; unavailable captions persist `transcript_unavailable`. No brittle scraping, browser, or audio transcription is introduced. Caption origin is recorded; unknown title/channel/language are not inferred.
- M2 provenance is `learner_file` or `learner_url`; future researched/generated sources require distinct origin contracts. Source data is never runtime instruction or learner evidence.
- Local reads are restricted to explicitly supplied regular files under `sources/`, rejecting traversal and symlinks/junctions, with a 32 MiB limit. HTTP accepts credential-free HTTP(S), bounded HTML responses and at most five redirects; no cookies/authentication/crawl. Relevant PPTX XML expansion is bounded. These checks do not create an OS sandbox against malicious concurrent local filesystem changes.
- Parser dependencies: PDF.js `pdfjs-dist` 6.4.299 (Apache-2.0), `fflate` 0.8.3 and `htmlparser2` 12.0.0 (MIT), installed without scripts. PDF.js's optional canvas 1.0.10 uses packaged native platform binaries, tested on Node 24.19.0/Windows x64. No ORM, browser, OCR, embedding or web framework is added.
- `/source add`, `list`, `status`, and `search` use the session's active course. Search combines safe literal-word AND via SQLite unicode61/BM25 with parameterized literal-presence constraints for distinct Unicode Symbol-category characters. Symbol-only queries use a stable literal fallback with rank 0. Mixed queries retain their operators; matching tests component presence within a segment, not formula structure or equivalence. Search allows 1–32 word/symbol components, and current versions and course/optional source filters apply on both paths. Historical versions remain inspectable.
- Portable tests use synthetic material; real Logic acceptance runs in an ignored isolated workspace through the pinned Pi SDK and checks original hashes. Private source files and all derived private artifacts stay ignored. No M3 features are introduced.

## Deferred review watchpoints

- Before later visual/hybrid re-extraction augments existing text, design explicit extraction revisions so historical segments referenced by evidence remain immutable. Identical-byte version reuse remains acceptable for M2; extraction revisions are not implemented here.
- Before URL ingestion can be invoked autonomously by a model/agent, review and implement SSRF restrictions for private, loopback and link-local addresses, including redirect handling. M2 remains explicitly user-directed; no networking/security subsystem is added in this correction.

## M4 engineering choices

The user authorized assessment/evidence foundation after the M3 checkpoint, with no learner-model or later-milestone behavior. The pre-coding report specified these implementation details:

- Immutable task snapshots resolve the active or explicit historical curriculum once and validate course-owned concept membership. Optional source/version/segment and separate research references use existing read ports. Task creation is separate from response submission, not a question-bank feature.
- Attempts preserve supplied responses, explicit assistance/hints and optional confidence/latency/runtime references. Historical curriculum, targets, novelty and representation are exposed through the immutable task reference. Evidence audit joins these records rather than copying source text.
- A combined assessment repository provides snapshot transactions and atomic evaluation/evidence transactions. Attempts persist before evaluator invocation. Migration 5 is additive; migrations 1–4 are unchanged. Append-only triggers protect history, and parent-last inserts with deferred child foreign keys seal task mappings and rubric scores at commit.
- Scored evaluations carry finite normalized correctness; partial scores require a task-specific rubric with every criterion scored. Unscored evaluations have null correctness and can create explicitly unscored evidence. Failed invocations retain a failed evaluation but no event; a new operation ID permits later evaluation of that same attempt.
- Evaluators return bounded, strictly validated outcome proposals only. Unknown identity/learner-state fields are rejected. Trusted application code supplies evaluator identity and policy version; adapters cannot write repositories. M4 includes deterministic evaluation, human recording and fake open-response adapters, without live Pi LLM evaluation or provider calls.
- Text normalization, numeric tolerance and set duplicate behavior are explicit task data. Choice responses use known identifiers. Numeric parsing accepts a complete finite decimal only; numeric/choice/set malformed responses become unscored rather than fabricated correctness. No expression/proof/code execution or semantic equivalence is added.
- Assistance and novelty remain separate enums. Intended dimensions are metadata only. Confidence is 0–1, latency at most one day in milliseconds, and hint count at most 100; these bounds are input limits, not pedagogical thresholds.
- Course-scoped submission/evaluation operation IDs store SHA-256 fingerprints of canonical validated requests. Same request returns the original outcome, including failures; changed requests conflict. Manual evaluation fingerprints include the outcome, while evaluator invocation fingerprints include attempt/evaluator/policy and supersession, before a proposal exists.
- Corrections append same-attempt supersession links, never overwrite history. Existing-parent foreign keys, new IDs and update/delete prohibition prevent cycles. Audit exposes all terminal heads without selecting an authoritative grade or reconciling learner state.
- Pi supplies read-only attempt/evidence audit commands scoped to its existing session selection. No model-facing evidence writer is registered. Core services and evaluator contracts remain independent of Pi and SQL.
- Acceptance responses are explicitly synthetic. A read-only SQLite backup of the approved M3 Logic acceptance database supplies only existing structural/provenance linkage; all M4 writes occur in an ignored isolated copy. No learner performance claim results.
- No dependency, mastery/readiness, gap, review, diagnostic, teaching, web UI or OpenClaw component is added. Live open-response context assembly/provider execution remains deferred behind the port.

## M5 engineering choices

The user authorized diagnostic probing only after the M4 checkpoint. These choices were reported before implementation and implement that bounded scope; they do not change the product architecture.

- Diagnostics belong to a course and an immutable curriculum version. One session may be in progress per course; starting with the same budget resumes it, while a different budget conflicts. Default budget 6, explicit bounds 1–20. No global active-diagnostic pointer is introduced.
- `prerequisite-frontier-v1` produces session-specific `not_probed`, `provisionally_supported`, `provisionally_unsupported`, `mixed` or `uncertain` findings. Single-target independent scored correctness 1/0 provides support/difficulty; assistance, hints, AI performance, partial/non-scored outcomes and evaluation-head conflicts remain uncertain. Confidence is excluded. Observation metadata remains distinct rather than becoming a scalar knowledge score.
- Current terminal M4 evaluations determine each attempt's contribution once. Same-course/version prior attempt IDs are sealed at start and influence selection priority only. They cannot create current-session findings or satisfy stopping coverage. Active sessions read corrections; completed summaries freeze their as-of terminal IDs, while audit exposes later history.
- Navigation uses only prerequisite edges, middle-depth candidates, branching tie-breaks, connected-region coverage and direct observations. Support checks dependents; other outcomes check prerequisites. Each concept is probed at most once per session. A frontier is a set of direct difficulty/uncertainty or untested-prerequisite recommendations. Graph closure may remove candidates beyond an observed boundary but never manufactures evidence.
- M5 external-review correction: deterministic grounded-context availability filters candidate selection from pinned provenance. Only absence of usable evidence returns unavailable; programming/configuration failures still throw. Unavailable candidates remain `not_probed` with no fabricated task, attempt or evidence. No remaining probeable candidate produces `no_eligible_probe`. Reference caps apply after usability filtering, preserving source-first hybrid context. Model/provider failures remain retryable and never blacklist a concept. No persistence change or policy-ID change is needed.
- Stops are budget exhaustion, sufficient direct coverage, bounded frontier, no eligible probe or learner abandonment. Skips count against budget without attempts/evidence. Generation failures are resumable and create no task; failed evaluations retain the actual attempt and permit explicit superseding retry. Abandonment keeps records without a completed frontier.
- A proposal-only generator receives bounded selected-node context, direct prerequisite titles and exact usable source/research references. Hybrid source context takes priority; generated courses use existing M3 research. No new retrieval is introduced. Trusted application code fixes target, curriculum, task type, representation, novelty and origin. Model output cannot navigate or mutate repositories.
- Closed recall/discrimination/prediction/procedure tasks use M4 deterministic text/choice/numeric/set grading. No live LLM/open-response evaluator is needed for M5. Rich explanations and repeated alternative-representation probing remain deferred. Expected answers are excluded from learner-facing task rendering; structural checks reject obvious answer-key markers without claiming semantic leakage detection.
- Pi hosts commands and an isolated in-memory model session with one content-proposal tool, three proposal-call opportunities and a three-minute deadline. No ambient extensions, context files, skills, filesystem/shell tools or model-facing evidence writers are exposed. Feedback during probing is neutral. Read-only audit remains explicit.
- Migration 6 adds session/probe and M4-link tables with scope constraints, unique active/pending indexes and sealed audit history. Migrations 1–5 stay unchanged. An optional synchronous M4 task-link callback makes task/probe creation atomic. Attempts/evaluations retain M4 idempotency; diagnostic links recover separately. No provider call occurs inside a database transaction.
- Portable tests use synthetic material and fake model turns with the actual pinned SDK. Real Logic and generated Python acceptance use isolated ignored copies of the existing M3 database and three explicitly synthetic depth-based profiles. They validate orchestration/provenance, not question quality or pedagogical optimality. Private source excerpts, answers, transcripts and generated reports stay outside version control and the review diff.
- No new dependency, durable mastery/readiness state, gap system, review scheduler, teaching engine, web UI or OpenClaw is added. M5 remains uncommitted pending external review; M6 has not begun.

## M6 engineering choices

- `bounded-instruction-v1` owns session-local navigation. Content proposals cannot provide identities, assistance, next moves, graph changes or learner classifications.
- Teaching sessions pin a curriculum. Completed compatible M5 frontier recommendations seed targets; explicit selection overrides them, and a grounded prerequisite root is the conservative fallback. Compatible active sessions resume; incompatible options require abandonment.
- Moves are activation, explanation, independent/guided practice, scaffold, teach-back and near transfer. Independent activation success takes a focused explanation/practice path; failure takes a minimal cue. Each interactive response uses M4. No content-only move creates performance evidence.
- Scaffold levels 0–4 map to none, minimal, guided, guided and worked solution. Hint receipts attach to the outstanding task. Explicit AI performance is distinguishable. Only a fresh independent task resets task-specific assistance.
- Per episode, one direct-prerequisite detour is allowed, with a persisted return stack capped at depth four. Returning delivers the original concept's selected scaffold before its practice. Two failed independent transfer checks end the episode needing more instruction; total moves default to 24, configurable 1–80.
- Teach-back follows the authorized capture-only option: an explicit task-specific open rubric, actual immutable response and unscored M4 evaluation. No keyword-based semantic grading or live LLM evaluator is introduced. Closed checks govern instructional completion; neither immediate success nor completion is durable mastery.
- Migration 7 adds teaching-specific sessions, moves, support receipts and M4 outcome links. No generic workflow abstraction or duplicated performance ledger. Existing source-derived/curriculum-generated task origins remain; a move link identifies teaching context without modifying migration 5's enum/checksum.
- Task/move creation uses M4's synchronous transactional link hook. Generation is outside transactions; optimistic revisions and M4-head snapshots reject stale proposals. Attempt/evaluation links recover by persistent operation IDs without duplicating performance. Final summaries are sealed.
- The pinned Pi SDK exposes only `propose_teaching_content` in a separate in-memory session, with ambient resources disabled. Low scaffolds receive public tasks; scoring keys are supplied only for an intentional level-four worked solution. Feedback uses bounded, explicitly untrusted actual learner text.
- Acceptance uses reviewed local private lesson content against actual Logic/Python curriculum provenance, with explicitly synthetic responses. It verifies meaningful content and orchestration, not live-provider content quality. Private catalogs, explanations, responses, reports and databases stay ignored.
- No packages changed, new dependency, mastery, gaps, reviews, web UI, OpenClaw or M7 implementation.

- Teaching-specific context selects bounded verbatim title-relevant windows from the same stored evidence; original anchors/warnings and research URLs remain visible. M5 context selection is unchanged. This addresses navigation-preface truncation without a retrieval dependency.

## M7 engineering choices

- The user approved adding assisted_difficulty while retaining the six specified bands. It distinguishes attributable scored failure with assistance, without independent positive evidence, from independent difficulty and positive assisted-only evidence. Latest independent failure takes precedence over assisted success. A mixed band retains conflicting independent results while blocking repair remains unresolved.
- Policies are evidence-state-v1, gap-escrow-v1, readiness-v1 and competence-profile-v1. State is a deterministic projection of M4 metadata, not a model verdict, preference or M5/M6 status. Calibration exposes confidence/outcome observations without inventing a calibration score or a competence gate.
- Single-concept, single-terminal-head, scored zero/one evidence changes categorical support/difficulty. Assistance, hints, AI work, partial/unscored/failed/missing evaluation and multi-concept ambiguity remain distinct. Multiple heads exclude that attempt. Ambiguous multi-concept tasks cannot demote established competence for all targets; unresolved single-concept head ambiguity blocks durable mastery.
- Explicitly reused stable concepts carry evidence across curriculum versions. Selected node type determines the competence profile. Misconception and assessment-objective nodes have not_applicable stages. Direct evidence can establish a concept's own competence despite missing prerequisite evidence, without propagating evidence to parents. Non-assessable metadata prerequisites do not demand an impossible competence stage.
- The 24-hour gate uses attempt time, not grading time. A distinct non-repeated later independent success is required; passing time alone does nothing. Original novelty is retained, while exact task/prompt reuse is detected separately and cannot fabricate positive transfer or delayed verification. Prompt fingerprints normalize whitespace only.
- Gap identity is immutable course/concept/dimension/trigger-attempt/policy with a UUID. Recurrence links and transitions live in revisioned snapshots because corrections can alter the current causal chain. Repeated failures share an active gap. Changed independent success can move OPEN or REPAIR_IN_PROGRESS to AWAITING_VERIFICATION; closure requires another changed independent success at least 24h after the awaiting event. Failure resets verification. AI work never repairs/closes a gap.
- Recomputing current terminal lineage may remove an obsolete gap from the current projection. Immutable identities and old revision snapshots remain. Current revisions preserve original M4 IDs; gap audit can inspect prior beliefs even when no current gap remains.
- Migration 8 adds revision/current-pointer, dimension/evidence, gap identity/snapshot/evidence and readiness tables. Frozen schema vocabularies avoid future policy-enum changes rewriting migration 8. Migrations 1–7 are unchanged. Parent-last insertion seals projections, foreign keys scope audit links, and refresh plus publication uses one synchronous transaction. A failed refresh preserves the previous pointer and M4 history.
- A new read-only M4 ledger adapter provides all relevant course attempts across versions, without response bodies, scoring keys, rationales or source text. No M4 write/evaluation rule, M5 navigation or M6 navigation changes. Historical schema-absence tests now verify that M4/M5 do not create learner-state revisions; the migration-7 historical test explicitly stops at schema 7.
- Fingerprints include interpreted graph/version, policies, original task/attempt metadata, hint/assistance/novelty/representation/confidence and terminal evaluation/evidence identities. The projection stores prompt hashes and references, not answers or source excerpts. Unchanged basis reuses a revision even when the clock advances; eligible-after timestamps are information only.
- Pi registers read-focused state/readiness/gap commands with active-course scoping and no arbitrary edits or model-facing competence writer. No dependency, statistical learner model, LLM evaluator, question bank, review scheduler, notification layer, web UI or OpenClaw is introduced.
- Acceptance uses isolated copies of populated approved M6 data with synthetic histories on previously unobserved stable Logic/Python concepts. Full M4 metadata, prior migration ledgers and original DB hashes remain unchanged. Reports explicitly label all performance as synthetic development data and stay ignored.

## M8 engineering choices

- The M8 handoff authorizes evidence-spacing-v1 (not official FSRS), review-queue-v1 and review-task-v1. Review items are scheduling intent, never evidence. M4 remains the sole performance ledger and M7 the sole competence/readiness/gap authority. No M7 band, profile, delay, escrow or recurrence rule changes.
- Candidate generation reads M7 waiting-for-delayed-evidence, AWAITING_VERIFICATION gaps and durable concepts. Delayed/gap dates are M7's canonical eligible-after values. OPEN/REPAIR requires instruction; missing profile dimensions do not become maintenance.
- A small read-only M7 competenceTimeline API replays the selected immutable revision's observations through the SAME M7 gap/dimension/readiness policies. It exposes stage transitions in attempt-time order under that revision's terminal evaluations. It neither allocates/publishes identities nor writes projections. This identifies the event establishing/re-establishing durability even if the scheduler starts late or intermediate projections were never saved. It is distinct from historical grading beliefs.
- Maintenance intervals are 3, 7, 14, 30 and capped 60 days. Each current qualifying review success counts once; corrections re-evaluate that contribution. The durability episode uses the M7 transition attempt, current node/profile requirements and stable concept ID. Difficulty followed by renewed durability starts a new stage-zero episode. Compatible reused concepts across versions retain history; similar titles and changed requirements do not silently inherit it.
- Assisted/AI/partial/unscored/ambiguous performance does not advance spacing. A still-relevant requirement gets a new independent opportunity at least 24h later and no earlier than M7 eligibility. Scored failures are performed reviews; M7 alone determines difficulty/gaps. Evaluator failure preserves an awaiting-evaluation item and retries the SAME attempt.
- Immutable ReviewItem identity holds semantic constraints, policy IDs, basis hash, original revision/gap, eligibility, due date and stage. review_progress is a constrained current projection; append-only events/outcome links retain lifecycle and original completion audit. Due/overdue is derived. One active/awaiting item per course and one pending semantic basis are enforced by indexes. No ReviewSession framework is needed.
- Reconciliation excludes wall-clock time and unrelated state-revision IDs from semantic item identity. It keeps unchanged pending requirements, supersedes invalid future items, records the new basis and preserves old/completed items. Schedule writes are atomic. M4 task creation and the review link use the existing synchronous transaction hook; model calls happen outside transactions.
- M4 operation IDs recover committed attempts after link failure. Outcome links commit before M7 refresh. A failed M7 refresh prevents future schedule advancement; a failed schedule write preserves previous review history/schedule and retries deterministically. Completed-item links are sealed; current correction links append without overwriting the original completion.
- Migration 9 adds review_items, review_progress, review_events, review_outcomes, review_reconciliations and review_task_origins. Composite FKs and scope triggers protect course/version/concept/state/gap/task/attempt/evaluation/evidence alignment. The origin extension exposes review_generated through the M4 adapter while retaining the original provenance-origin column. Existing performed tasks cannot acquire that extension. The historical origins enum remains frozen because migration 5 imports it; current validation uses a separate extended enum. No prior migration or table rebuild is needed.
- Due queue classes are overdue/due gap, overdue/due delayed, then overdue/due maintenance. Within a class, greater lateness wins; equal lateness interleaves concept, dimension, type and representation, followed by stable IDs. Target selection uses M7 required dimensions, independent recency/count and coverage. Transfer requires near-transfer novelty; other review targets default to isomorphic. Exact task/prompt reuse, including trigger/repair prompts, cannot qualify.
- ReviewTaskGenerator proposes content/scoring/pinned provenance only in an isolated pinned Pi session. No ambient shell/filesystem/extensions/MCP, research, scheduler writer or learner-state writer. Closed structured checks are supported; rich explanation remains unscored/outside the review generator. Validation establishes structure/provenance identity, not semantic truth or novelty.
- Pi commands delegate active-course operations, render public tasks without scoring keys, accept rich JSON answers and expose bounded audit. M8 composition constructs the existing M7 services that M7's command registration omitted; no M7 policy is changed. No global selected course or persisted deadline feature is introduced. The pure queue accepts an optional future deadline context without relaxing earliest-at or priority classes.
- Acceptance uses isolated read-only backups of approved M7 Logic/Python workspaces and reviewed private content catalogs. All added performance is explicitly synthetic development data; original hashes, historical ledgers and complete prior audit rows are preserved. Reports and catalogs remain ignored. No dependency, new retrieval, official FSRS, question bank, background job, notification, OpenClaw, web UI or M9 implementation is added.
